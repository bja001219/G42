# AI-assisted development: 위임보다 수용 판정에 초점을 둔 개발

이 프로젝트는 AI 코딩 에이전트를 구현 가속 수단으로 사용했습니다. 다만 에이전트가
기능 목록을 임의로 정하거나 생성 결과를 그대로 병합하는 방식은 피했습니다. 제가
공용 계약과 동기화 경계를 먼저 고정하고, 서로 독립적인 작업만 나누어 위임한 뒤,
테스트와 실제 실패 시나리오를 기준으로 최종 수용 여부를 판단했습니다.

## 제가 직접 책임진 영역

- `GameDefinition` / `GameSession` / `RoomService` 계약과 게임 등록 구조
- Firestore 문서에 저장되는 상태 스키마와 플레이어별 부분 갱신 경계
- 온라인·로컬 전송 구현의 교체 가능성 및 화면과 게임 로직 사이의 의존 방향
- 동시 입력, 재접속, 상대 이탈, 재대국처럼 정상 경로 밖에서 발생하는 상태 전이
- 공개 데모의 보안 범위, 알려진 제약, 최종 배포 가능 여부

AI 에이전트에는 게임별 정형 구현, 반복 UI, 규칙 케이스 확장과 테스트 초안 작성을
주로 맡겼습니다. 각 작업은 `lib/games/<id>/`처럼 충돌이 적은 경계로 제한했고,
공용 코어를 임의로 수정하지 못하게 했습니다. 실제 작업 분할 기준과 입력 계약은
[`HANDOFF_PROMPTS.md`](HANDOFF_PROMPTS.md)에 남겨 두었습니다.

## 수용 판정 절차

1. **계약 선행**: 구현 전에 [`GAME_CONTRACT.md`](GAME_CONTRACT.md)로 상태 표현,
   turn/winner 갱신, 온라인·로컬 동작 조건을 고정했습니다.
2. **격리 위임**: 에이전트별 수정 디렉터리와 읽기 전용 경계를 명시해 병렬 작업의
   충돌과 공용 구조의 무단 변경을 줄였습니다.
3. **diff 리뷰**: 생성 코드가 최신 `room.state`를 기준으로 갱신하는지, 한 사용자의
   쓰기가 다른 사용자의 값을 덮지 않는지, 종료 상태가 양쪽에 동일하게 보이는지
   중심으로 검토했습니다.
4. **자동 검증**: 순수 게임 규칙, Firestore round-trip, 동시 갱신 no-clobber,
   재접속/presence, 작은 화면 overflow를 테스트로 고정했습니다.
5. **실패 기반 보완**: 실제 발견된 동시 탭 clobber, 재대국 soft-lock, 결과 화면
   비대칭 문제는 재현 테스트를 먼저 남긴 뒤 수정했습니다.

현재 `test/`에는 게임 규칙과 화면·동기화 회귀 테스트가 함께 있습니다. CI는 모든
변경에서 `flutter analyze`, `flutter test`, `flutter build web`을 실행합니다. 테스트가
통과해도 Firestore 운영 권한이나 실제 두 기기 네트워크 동작은 별도 검증 대상이며,
데모용 익명 인증을 제품 수준 사용자 권한 모델로 오해하지 않습니다.

## 알려진 기술 부채

- 일부 게임 화면 파일은 규칙이 늘면서 1,000줄을 넘었습니다. 신규 기능을 더하기 전
  controller / presentation / dialog 단위로 분리할 대상입니다.
- 현재 Firestore 규칙은 인증된 데모 사용자만 허용하지만, 방 멤버별 권한까지 검증하는
  운영 수준 규칙은 아닙니다.
- Firebase 미설정 시 사용하는 로컬 서비스는 개발 폴백입니다. 현재 UX의 중심은 두
  기기 온라인 대전이며, 동일 기기 핫시트는 별도 진입 흐름 정리가 필요합니다.

이 문서의 목적은 AI 사용 사실을 감추는 것이 아니라, 무엇을 위임했고 어떤 근거로
결과를 받아들였는지 검토 가능한 형태로 남기는 것입니다.
